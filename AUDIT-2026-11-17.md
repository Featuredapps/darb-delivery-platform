# DARB pre-release audit — 2026-11-17

## Scope and decisions
- Release scope: customer, vendor, driver, and admin roles.
- Payment: cash on delivery at launch; online payment remains disabled until a provider is selected, integrated, and tested.
- Launch: closed testing before public release.
- No paid services, top-ups, or SMS sends without explicit owner approval.

## Verified checks
- Latest `main` inspected at `13cfc8e` before this audit.
- Backend dependencies installed from the source archive.
- Prisma schema validation passed when a non-production placeholder `DATABASE_URL` was supplied.
- Prisma Client generation passed.
- NestJS production build passed.
- Backend Jest suite passed: 1 suite, 5 tests. Current suite only covers Syrian phone normalization.
- Flutter SDK is not installed in the audit workspace, so no local Flutter analyze/build/device test was performed.

## Findings — ordered by release risk

### P0 — production infrastructure is not suitable for live commerce
- `FREE-DEPLOYMENT.md` and `backend/DEPLOYMENT.md` explicitly classify Render Free + Supabase Free + Upstash Free as preview/test infrastructure, not production. Free services can sleep/pause, quota out, and Supabase Free has no automatic backups.
- Do not accept real customer data or live orders on this setup. Production durability, backup/restore, capacity and availability need an approved infrastructure decision.

### P0 — SMS configuration documentation is inconsistent with the implemented provider
- `backend/src/modules/auth/auth.module.ts` and `sms.providers.ts` implement `SMS_PROVIDER=msgplus` with `MSGPLUS_API_KEY`, `MSGPLUS_SENDER_NAME`, and `MSGPLUS_TEMPLATE_ID`.
- Existing deployment documentation still describes the older generic `SMS_API_URL` / `SMS_API_KEY` adapter. Correct documentation and verify Render environment configuration without sending SMS first.
- Live OTP delivery remains unverified; no SMS was sent during this audit.

### P1 — admin role has no mobile admin experience
- Backend exposes pending vendor/driver lists and status update routes under `/admin`.
- Flutter app shell routes CUSTOMER and VENDOR explicitly, then routes every other role to the driver interface. ADMIN therefore receives driver screens and cannot operate admin queues.

### P1 — production Android manifest permits cleartext traffic
- Source `AndroidManifest.xml` sets `android:usesCleartextTraffic="true"`. Release configuration must enforce HTTPS and reject cleartext connections.

### P1 — mobile API client has no refresh-token flow
- It stores `refreshToken`, but the request client does not refresh expired access tokens or retry once after 401. This can strand active sessions after access-token expiry.

### P1 — core delivery capabilities remain incomplete
- Mobile customer home explicitly says maps/live tracking are not available until a map provider and location service are configured.
- Firebase push notifications and production maps/geocoding are documented as not integrated/verified.
- Driver location update endpoint and end-to-end live tracking are not exposed in the inspected mobile UI/API client.

### P1 — order/payment behavior is incomplete for the approved release scope
- Current order creation always creates `CASH_ON_DELIVERY` payment records and the checkout UI only offers cash on delivery.
- Online payment must remain clearly marked unavailable until provider selection and secure payment lifecycle integration; no online payment provider is configured.
- Order delivery fee currently selects the lowest `feeBase` delivery zone for a city and does not calculate distance-based `feePerKm` in the inspected service.

### P1 — automated coverage is insufficient
- Only one backend spec file exists and it contains five phone normalization tests.
- No order lifecycle, role authorization, OTP lifecycle, payment, vendor/driver application, or Flutter widget/integration tests were found in the source archive.

### P2 — source/build process is fragile
- Main application source is stored inside `DARB-source.zip`; CI extracts it and overlays patches. Android scaffold is regenerated during CI and additional UI/API overrides are copied during build. This makes local development, review, and reproducible releases harder.
- The checked-in Android manifest and build scaffold are partial; CI currently repairs them rather than maintaining a complete Android project in source control.

## First repair sequence
1. Add a dedicated ADMIN mobile route and vendor/driver approval queues.
2. Enforce HTTPS/cleartext prohibition in release builds.
3. Implement refresh-token rotation/retry and session-expiry handling.
4. Add order lifecycle and authorization tests, then Flutter widget/integration tests.
5. Complete fee calculation and delivery tracking contracts.
6. Correct provider documentation and run an explicitly approved SMS test only after all non-spending checks pass.
7. Integrate and test Firebase/maps, then execute closed beta.
8. Move to approved production-grade hosting, configure backups/restore, signing, privacy disclosures, and Play release artifacts.

## Explicit limitations
- This is a source-level audit, not a penetration test or device acceptance test.
- No SMS, paid API, infrastructure upgrade, or real payment operation was performed.
- Successful backend build/tests do not establish production readiness.
